# INC-20260529-001：release 脚本自发布导致本地仓库清洗事故（脱敏摘要）

> 可公开版本
> 事故编号：INC-20260529-001
> 日期：2026-05-29
> 等级：P0

---

## 事故摘要

v0.6.40 发布过程中，release 脚本在处理中文路径时出现 bug。
v0.6.41 修复脚本时，总控决策让修复后的 release 脚本自行发布。
执行后，rsync 的危险参数导致仓库根目录被清成静态产物，核心目录一度消失。
重新 clone 仓库后恢复。

---

## 事故等级

**P0**：本地仓库数据一度丢失，已恢复。

---

## 时间线

1. v0.6.40 文章发布成功，release 脚本暴露中文路径处理 bug
2. v0.6.41 修复脚本，总控决策用 release 脚本自发布
3. rsync 危险操作导致仓库根目录被清洗
4. 发现后重新 clone 恢复

---

## 直接原因

发布工具自发布形成循环依赖，rsync --delete 在错误目录执行时清洗了整个仓库。

---

## 深层原因

1. 发布工具自发布是循环依赖，风险叠加
2. rsync --delete 是高危操作，需要明确目录边界隔离
3. 事故发生后未按"先查状态再决定"原则执行

---

## 新增规则（五条）

**1. 发布工具永远不能自发布。**
修复 release 脚本后的版本，由本地 Mac 手动 git 操作发布，不通过 release 脚本自发布。

**2. 事故后必须先查状态，不得重跑长流程。**
任何发布中断后，第一动作是 `git status` 和 `ls` 确认当前状态，再决定下一步。未确认状态前不得重跑。

**3. 重大事故必须编号归档。**
每次 P0 / P1 事故必须写编号报告、复盘、新规则。不归档的事故视为未解决。

**4. rsync --delete 必须有明确目标目录，禁止在仓库根目录直接执行覆盖自身。**
rsync 源和目标必须明确分离，危险参数必须在脚本中注释警告。

**5. Docker bind mount 危险操作必须先确认路径。**
任何涉及 bind mount 的高危操作前，必须确认当前目录和挂载路径。

---

## 教训

1. 发布工具自发布是循环依赖，会导致风险叠加。
2. 高危操作（rsync --delete）必须做二次确认。
3. 事故经验不归档，下次同类事故必重演。
